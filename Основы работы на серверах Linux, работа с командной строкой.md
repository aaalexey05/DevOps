## 6. Сравнение sudo и su
### Использованные команды
```bash
sudo id
sudo -i
id
exit
su -c "id"
```
###  Описание
На этом этапе сравниваются два подхода к получению привилегий администратора. `sudo id` запускает одну команду с правами суперпользователя, `sudo -i` открывает интерактивную root-сессию, а `su -c "id"` выполняет указанную команду через механизм `su`. Это позволяет на практике увидеть разницу между временным повышением привилегий и полноценным переключением пользователя.

## 7. Найстройка отдельного правила в /etc/sudoers.d
### Использованные команды
```bash
echo 'jarservice ALL=(root) NOPASSWD: /usr/bin/id' | sudo tee /etc/sudoers.d/jarservice-id  
sudo chmod 440 /etc/sudoers.d/jarservice-id  
sudo visudo -c
```
###  Описание
Для пользователя `jarservice` создаётся отдельное правило в каталоге `/etc/sudoers.d`, разрешающее выполнять команду `/usr/bin/id` от имени `root` без ввода пароля. Далее задаются правильные права доступа к файлу и выполняется проверка синтаксиса конфигурации с помощью `visudo -c`.

## 10. Локальная и глобальная переменные оболочки
### Использованные команды
```bash
LOCAL_VAR="local_value"
GLOBAL_VAR="global_value"
export GLOBAL_VAR

echo "$LOCAL_VAR"
echo "$GLOBAL_VAR"

bash
echo "$LOCAL_VAR"
echo "$GLOBAL_VAR"
exit
```
###  Описание
Создаются две переменные оболочки: локальная `LOCAL_VAR` и экспортированная `GLOBAL_VAR`. После запуска вложенной `bash`-сессии проверяется, какие переменные сохраняются. Локальная переменная доступна только в текущей оболочке, а экспортированная наследуется дочерним процессом. В твоём файле сам запуск `bash` между проверками лучше явно показать именно так, иначе сравнение будет неполным.

## 13. Работа со `screen` 
### Использованные команды
```bash
screen -S my_screen  
i=1; while true; do clear; echo "Счетчик: $i"; i=$((i+1)); sleep 1; done  
screen -ls  
screen -r my_screen  
screen -ls
```
###  Описание
Создаётся отдельная `screen`-сессия `my_screen`, внутри которой запускается бесконечный цикл со счётчиком. После отсоединения и повторного подключения проверяется, что процесс продолжал работать.  
Чтобы сессия осталась живой, для отсоединения нужен **`Ctrl + A`, затем `D`**. Если нажать `Ctrl + C`, процесс просто остановится.

## 15.  Создание `monitoring.service`
### Использованные команды
```bash
sudo tee /etc/systemd/system/monitoring.service > /dev/null <<'EOF'  
[Unit]  
Description=Monitoring service  
  
[Service]  
Type=oneshot  
ExecStart=/usr/bin/free -h  
  
[Install]  
WantedBy=multi-user.target  
EOF
```
###  Описание
Создаётся unit-файл `monitoring.service` в каталоге `/etc/systemd/system`. В качестве демонстрационной команды используется `/usr/bin/free -h`, которая выводит информацию об оперативной памяти.

## 16.  Создание `monitoring.timer`
### Использованные команды
```bash
sudo tee /etc/systemd/system/monitoring.timer > /dev/null <<'EOF'  
[Unit]  
Description=Run monitoring.service every minute  
  
[Timer]  
OnCalendar=*-*-* *:*:00  
Unit=monitoring.service  
  
[Install]  
WantedBy=timers.target  
EOF
```
###  Описание
Создаётся таймер `monitoring.timer`, который запускает сервис `monitoring.service` по расписанию, заданному параметром `OnCalendar`. Это позволяет продемонстрировать работу timer-юнитов `systemd`.

## 18.  Просмотр логов сервиса и запуск таймера
### Использованные команды
```bash
journalctl -u monitoring.service -n 20
journalctl -u monitoring.service --since "2026-04-09 00:00:00" --until "2026-04-09 23:59:59"

systemctl start monitoring.service
journalctl -u monitoring.service -n 20 --no-pager

systemctl enable --now monitoring.timer
systemctl status monitoring.timer --no-pager
systemctl list-timers --all | grep monitoring
```
###  Описание
Сначала выполняется просмотр журнала `monitoring.service`. Если сервис ещё не запускался, журнал может быть пустым. После ручного запуска `monitoring.service` и включения таймера `monitoring.timer` проверяется журнал, статус таймера и его наличие в списке активных таймеров. Это подтверждает, что созданные unit-файлы работают корректно.
